# Справочник метрик эксперимента (`report.csv`)

Документ описывает **все 28 колонок** файла [report.csv](report.csv): откуда берутся значения, что означают в Galois, как их интерпретировать при сравнении BFS / PageRank / SSSP / Triangle Counting (TC).

**Источники данных:**
- `-statFile` → CSV-статистика Galois (`experiments/results/stats/*.stats`);
- парсер: `parse_galois_stat.py` (логика `Galois/scripts/galois_log_parser.R`);
- для `inspect_bytes` / `load_bytes` у BFS/PR/SSSP — дополнительно `experiments/results/run.log` (`parse_run_log.py`), если в stat нет байтов.

**Единицы времени в stat:** микросекунды (μs), в отчёте — **миллисекунды** (значения из stat уже в тех единицах, что пишет Galois для Timer_*; для GraphConstructTime / Edge* — как в HMAX/HSUM).

**Единицы объёма:** байты (суммы HSUM — суммарно по MPI-процессам, если не указано иное).

---

## Часть A. Идентификаторы прогона (8 колонок)

Эти поля не из таймеров Galois, а описывают **конфигурацию и результат** одного экспериментального запуска.

### 1. `algorithm`

**Что это:** название алгоритма.

**Значения:** `BFS`, `PageRank`, `SSSP`, `Triangle Counting`.

**Зачем:** ключ для сравнения разных бенчмарков на одном графе и при одном числе MPI-процессов. У каждого алгоритма свой бинарник, свой регион статистики (`BFS`, `PageRank`, `SSSP`, `TC`) и разная схема коммуникации (см. `sync_bytes` для TC).

---

### 2. `dataset`

**Что это:** имя входного графа (без расширения).

**Значения:** `web-Google`, `roadNet-PA`, `wiki-talk-temporal`.

**Зачем:** размер и структура графа (число вершин/рёбер, степень) сильно влияют на время и трафик. Для TC на `wiki-talk-temporal` использовался очищенный граф `wiki-talk-temporal-clean.sgr` (без петель и кратных рёбер).

---

### 3. `mpi_processes`

**Что это:** число MPI-процессов (`mpirun -np N`).

**Значения в эксперименте:** 1, 2, 4, 6, 8.

**Зачем:** основная ось **слабого масштабирования** (weak scaling): как меняются время и коммуникация при росте числа процессов на одной машине. Запуски с `-np 2` требуют `mpirun --bind-to none` (см. [REPRODUCE.md](REPRODUCE.md)).

---

### 4. `threads`

**Что это:** число потоков OpenMP на процесс, параметр `-t=...`.

**В эксперименте:** задано `2`; в stat часто попадает `Threads` с HOST_0 (фактически может отображаться `1` — особенность distributed stat).

**Зачем:** влияет на параллелизм **внутри** каждого MPI-ранга; не путать с `mpi_processes`.

---

### 5. `runs`

**Что это:** число повторов бенчмарка, `--runs=3` (в stat: `Runs`).

**Зачем:** по нескольким прогонам усредняются `Timer_0`, `Timer_1`, … → `total_time_exec`, `compute_time`, `sync_time`. Один прогон в stat часто обозначается суффиксом `_0`, `_1`, `_2` в категориях.

---

### 6. `primary_metric`

**Что это:** имя **рекомендуемой** метрики для сравнения производительности данного алгоритма.

**Значения:**
| Алгоритм | primary_metric |
|----------|----------------|
| BFS, PageRank, SSSP | `compute_time` |
| Triangle Counting | `total_time_exec` |

**Зачем:** у push-алгоритмов (BFS/PR/SSSP) основное время — в `do_all` (вычисления на рёбрах/вершинах); у TC итеративной Gluon-синхронизации почти нет, удобнее смотреть среднее `Timer_i`.

---

### 7. `primary_metric_value`

**Что это:** числовое значение `primary_metric` для этой строки.

**Зачем:** быстрый столбец для графиков «время vs MPI» без выбора вручную. Для TC совпадает с `total_time_exec`; для BFS — с `compute_time`.

---

### 8. `status`

**Что это:** успешность прогона и наличие stat-файла.

**Значения:**
- `ok` — есть валидный `.stats` с `TimerTotal`;
- `segfault_mpi2` / `no_stat_file` — прогон не удался или stat отсутствует (в полном эксперименте после исправления MPI=2 обычно `ok`).

**Зачем:** пустые метрики в строке с ошибкой **не означают ноль** — данных нет.

---

## Часть B. Время и синхронизация алгоритма (10 колонок)

Эти метрики описывают **фазу после построения графа**: инициализация + повторы бенчмарка + синхронизация Gluon (для push-алгоритмов).

### 9. `total_time`

**Stat:** `TimerTotal`, регион бенчмарка (`BFS`, `PageRank`, …), агрегация **HMAX** по хостам.

**Что измеряет:** **полное время** от начала выполнения бенчмарка до записи stat, включая:
- построение распределённого графа (`GraphConstructTime`);
- все прогоны `--runs`;
- финализацию.

**Как читать:**
- растёт с числом MPI не только из-за коммуникации, но и из-за накладных расходов и неидеального баланса;
- для сравнения «чистого» алгоритма часто смотрят `total_time_exec` или `compute_time`;
- **всегда ≥** `graph_construct_time` + время прогонов.

**Пример смысла:** при росте `mpi_processes` `total_time` может расти (больше координации), даже если `compute_time` на один do_all падает.

---

### 10. `total_time_exec`

**Stat:** категории `Timer_0`, `Timer_1`, `Timer_2`, … — **среднее** по прогонам (как в `galois_log_parser.R`: mean of Timer_i).

**Что измеряет:** среднее время **одного полного прогона** бенчмарка (без повторного построения графа между runs; граф строится один раз, затем несколько Timer_i).

**Как читать:**
- для **TC** — главная метрика времени подсчёта треугольников;
- для BFS/PR/SSSP — близко к «wall-clock одного run», но может включать часть накладных расходов вне отдельных `Sync_*`;
- сравнивать между MPI: ожидаемое ускорение, если алгоритм масштабируется.

**Отличие от `compute_time`:** `total_time_exec` — таймер уровня всего run; `compute_time` — сумма регионов `do_all` внутри run.

---

### 11. `compute_time`

**Stat (BFS/PR/SSSP):** сумма по регионам вида `<Benchmark>_<run>_<iter>` (например `BFS_0_0`, …), усреднение по `--runs`; отражает **do_all** / основные вычислительные фазы.

**Stat (TC):** среднее по `TC_0`, `TC_1`, `TC_2` только для категории **`Time`** (исключены `Iterations`, чтобы не смешивать счётчики работы с временем).

**Что измеряет:** время **полезных вычислений** на локальных/partition данных, без явного учёта `Sync_*` (они в `sync_time`).

**Как читать:**
- **меньше — лучше** при том же графе и N;
- для PR на больших графах обычно **больше**, чем BFS (много итераций PageRank);
- для TC в вашем отчёте порядок ~3k ms (время), не путать со старым багом парсера (суммирование Iterations).

**Связь с `primary_metric`:** для BFS/PR/SSSP = `primary_metric_value`.

---

### 12. `sync_time`

**Stat:** категории `Sync_<Benchmark>_<run>_<phase>`, усреднение по runs (mean per run, then mean across runs — как в R-парсере).

**Что измеряет:** суммарное время, проведённое в **явных синхронизациях Gluon** (`sync()`): обмен граничными данными, bitmap, reduction для push-алгоритмов на каждой итерации/фазе.

**Как читать:**
- при росте MPI часто **растёт** (больше границ, больше раундов sync);
- для **TC** в ваших логах обычно **0** — нет `Sync_TC_*`;
- высокий `sync_time` при низком `compute_time` → узкое место в коммуникации, а не в CPU.

**Не путать с:** `sync_bytes` (объём) и с `inspect_bytes`/`load_bytes` (построение графа).

---

### 13. `barrier_time`

**Stat:** регион `DGReducible`, категории `ReduceDGAccum_<run>_<...>`, усреднение по runs.

**Что измеряет:** время в **неявных барьерах** при редукциях на структуре `DGReducible` (Galois distributed reduction), не обязательно совпадает 1:1 с каждым `Sync_*`.

**Как читать:**
- дополнение к `sync_time` для анализа «ожиданий» между фазами;
- часто 0 или мало на ваших прогонах BFS;
- рост с MPI может указывать на дисбаланс нагрузки между рангами.

---

### 14. `sync_bytes`

**Stat:** сумма **HSUM** по категориям `ReduceSendBytes_<Benchmark>_0` и `BroadcastSendBytes_<Benchmark>_0` (только **первый прогон** `_0`, как в `galois_log_parser.R`).

**Что измеряет:** **объём данных (байты)**, отправленных в MPI-reduce/broadcast во время **синхронизации алгоритма** (фаза Gluon, не построение графа).

**Как читать:**
- аналог метрики однокурсницы **ReduceSendBytes** (если она не суммирует broadcast);
- при увеличении MPI часто **растёт** (больше обмена на границах);
- для **TC = 0** — нормально: distributed TC не использует эти счётчики;
- сравнивать с `inspect_bytes` + `load_bytes`: те — **другая фаза** (construction).

**Пример:** BFS `web-Google`, 4 MPI → `sync_bytes` ≈ 10 MB; TC → 0.

---

### 15. `graph_construct_time`

**Stat:** `GraphConstructTime`, **HMAX** (максимум среди хостов).

**Что измеряет:** время **построения распределённого графа** на всех MPI-процессах: чтение файла, partition, inspection, loading, allocation — до вызова `InitializeGraph` / начала бенчмарка.

**Как читать:**
- входит в `total_time`, но не в `total_time_exec` отдельно по каждому run (граф строится один раз);
- растёт с MPI из-за коммуникации при inspection/loading (`inspect_bytes`, `load_bytes`);
- для TC на больших графах может быть **секунды** (7904 ms для web-Google 4p).

**Связь:** `edge_inspection_time` + `edge_loading_time` — компоненты внутри этой фазы (таймеры, не полная сумма).

---

### 16. `replication_factor`

**Stat:** `ReplicationFactor`, регион **Gluon**, HOST_0 (среднее/фактор репликации для push-алгоритмов).

**Что измеряет:** насколько **вершины/данные реплицируются** между хостами сверх минимального partition (1.0 = без лишней репликации в среднем по модели Gluon).

**Как читать:**
- значения **> 1** (например 1.01–2.8) — часть данных дублируется на нескольких рангах для ускорения доступа;
- рост с MPI может увеличивать фактор;
- для **TC** часто **0** в этой колонке — mining-граф использует другие поля (`replication_nodes` / `replication_edges`).

---

### 17. `comm_mem_max`

**Stat:** `CommunicationMemUsageMax`, **HMAX** (по всей системе stat).

**Что измеряет:** **максимальный** объём памяти, зарезервированный/использованный под **коммуникационные буферы** Galois (обмен между хостами).

**Как читать:**
- 0 в ваших прогонах — счётчик мог не включаться в сборке или не превышать порог отчёта;
- если > 0: пиковая потребность в RAM для MPI/Gluon buffers при данном N и графе.

---

### 18. `comm_mem_min`

**Stat:** `CommunicationMemUsageMin`, **HMIN**.

**Что измеряет:** **минимальный** зарегистрированный объём коммуникационной памяти (нижняя оценка по хостам).

**Как читать:** вместе с `comm_mem_max` — разброс использования буферов; у вас часто 0.

---

## Часть C. Построение распределённого графа (10 колонок)

Метрики фазы **до** BFS/PR/SSSP/TC: как граф **разрезается** и **загружается** на MPI-процессы. Источник: `dGraph_Generic` (BFS/PR/SSSP) или `dGraph_Mining` (TC).

### 19. `inspect_bytes`

**Stat:** `EdgeInspectionBytesSent`, **HSUM** (сумма по всем хостам).

**Fallback:** сумма из `run.log` строк `Edge inspection time: ... to read N bytes` по всем MPI-рангам.

**Что измеряет:** сколько **байт** отправлено между процессами на фазе **inspection** — предварительный обмен метаданными: какие рёбра/зеркала нужны на каждом хосте **до** физической загрузки рёбер.

**Как читать:**
- аналог **inspect_bytes** у однокурсницы;
- растёт с **числом MPI** и размером графа;
- для BFS/PR/SSSP часто **пусто** в CSV, если в stat нет счётчика и в log не сохранился вывод (см. примечание в [REPRODUCE.md](REPRODUCE.md));
- для **TC** заполнено (например ~22 MB inspect для web-Google 4p).

**Смысл для сравнения:** «стоимость узнавания структуры графа» при распределении; не включает полную загрузку рёбер (`load_bytes`).

---

### 20. `load_bytes`

**Stat:** `EdgeLoadingBytesSent`, **HSUM**.

**Fallback:** `run.log`, строки `Edge loading time: ... to read N bytes`.

**Что измеряет:** объём **байт**, переданных при **загрузке рёбер** на владеющие хосты после inspection.

**Как читать:**
- аналог **load_bytes** у однокурсницы;
- обычно **больше** `inspect_bytes` (передаются реальные данные рёбер);
- для TC на web-Google 4p: ~55 MB load vs ~22 MB inspect;
- пустое поле у BFS 1/4/6/8 — та же проблема лога, что у `inspect_bytes`.

**Связь с `total_time`:** большие `load_bytes` → больший `graph_construct_time`.

---

### 21. `load_messages`

**Stat:** `EdgeLoadingMessagesSent`, **HSUM**.

**Что измеряет:** **число MPI-сообщений** (не байты!), отправленных при фазе загрузки рёбер.

**Как читать:**
- высокое число при малом среднем размере сообщения → много мелких пакетов (накладные расходы MPI);
- для TC web-Google 4p: всего **12** сообщений на весь HSUM — мало крупных передач;
- пусто у BFS — счётчик не записан в stat для generic loader.

---

### 22. `peak_load_bytes`

**Stat:** `EdgeLoadingMaxBytesSent`, **HMAX**.

**Что измеряет:** **максимальный** объём байт, отправленных **одним** хостом за одну передачу/фазу loading (пик нагрузки на самый «тяжёлый» ранг).

**Как читать:**
- выявляет **дисбаланс**: один ранг отправил до 5 MB, сумма `load_bytes` — 55 MB;
- для анализа узких мест сети «худший» процесс;
- только mining/TC в ваших stat (BFS — пусто).

---

### 23. `replication_nodes`

**Stat:** `ReplicationFactorNodes` (mining, HOST_0) или fallback → `ReplicationFactor` (Gluon) для BFS/PR/SSSP.

**Что измеряет:** коэффициент **репликации вершин** при mining-partition (сколько раз в среднем вершина учтена с репликацией на границах).

**Как читать:**
- **1.0** — почти без репликации вершин;
- **~1.8** для TC web-Google 4p — заметная репликация узлов на границах partition;
- для BFS совпадает с `replication_factor` (~1.01).

---

### 24. `replication_edges`

**Stat:** `ReplicatonFactorEdges` (опечатка **Replicaton** в исходниках Galois).

**Что измеряет:** коэффициент **репликации рёбер** (mining), аналогично узлам, но для рёбер/proxy edges.

**Как читать:**
- для TC web-Google 4p: ~**2.08** — рёбра реплицируются сильнее, чем узлы;
- пусто для BFS/PR/SSSP (нет mining stat);
- высокий фактор → больше памяти и обмена при построении mining-графа.

---

### 25. `total_node_proxies`

**Stat:** `TotalNodeProxies`, HOST_0 (значение с одного reporting host, не HSUM).

**Что измеряет:** сколько **proxy-вершин** (удалённых вершин, представленных локально) создано при распределённом представлении mining-графа.

**Как читать:**
- масштаб **распределённой структуры**; для web-Google TC 4p: 1 642 152 proxies при ~916k вершин графа;
- пусто для BFS — generic partitioner не пишет эту категорию;
- рост с MPI — больше граничных vertex proxies.

---

### 26. `total_edge_proxies`

**Stat:** `TotalEdgeProxies`, HOST_0.

**Что измеряет:** число **proxy-рёбер** (рёбра, принадлежащие удалённым частям графа).

**Как читать:**
- для TC отражает объём граничных рёбер; web-Google 4p: ~10.6M proxies;
- вместе с `total_node_proxies` показывает, насколько partition «раздувает» представление графа;
- пусто для BFS/PR/SSSP в stat.

---

### 27. `edge_inspection_time`

**Stat:** `EdgeInspection`, **HMAX** (микросекунды → в отчёте как число, например 304).

**Что измеряет:** **время** (не байты!) фазы inspection на **самом медленном** хосте.

**Как читать:**
- заполнено для **всех** BFS/PR/SSSP в stat, даже когда `inspect_bytes` пусто;
- сравнение MPI: рост времени inspection при росте N;
- **не суммируется** с `inspect_bytes` — это разные измерения (секунды vs байты).

---

### 28. `edge_loading_time`

**Stat:** `EdgeLoading`, **HMAX**.

**Что измеряет:** **время** фазы загрузки рёбер на худшем хосте.

**Как читать:**
- аналогично `edge_inspection_time` для фазы loading;
- для BFS обычно **больше** inspection time (loading тяжелее);
- при отсутствии `load_bytes` в CSV всё равно можно сравнить относительную стоимость loading по времени.

## Сводная таблица: что с чем сравнивать

| Вопрос | Смотрите колонки |
|--------|------------------|
| Как быстро работает BFS/PR/SSSP? | `compute_time`, `primary_metric_value` |
| Как быстро работает TC? | `total_time_exec`, `compute_time` |
| Сколько ждём синхронизации в push-алгоритме? | `sync_time`, `barrier_time` |
| Сколько данных в sync алгоритма? | `sync_bytes` (не для TC) |
| Сколько стоило **построить** граф? | `graph_construct_time`, `inspect_bytes`, `load_bytes` |
| Сравнение с однокурсницей (construction) | `inspect_bytes`, `load_bytes` |
| Сравнение с однокурсницей (algorithm comm) | `sync_bytes` ≈ ReduceSendBytes |
| Дисбаланс / репликация mining (TC) | `replication_nodes`, `replication_edges`, `peak_load_bytes` |
| Масштаб распределённого графа (TC) | `total_node_proxies`, `total_edge_proxies` |

## Типичные паттерны по алгоритмам

### BFS / PageRank / SSSP
- Есть **`sync_time`**, **`sync_bytes`**, **`replication_factor`** (Gluon).
- **`inspect_bytes` / `load_bytes`** — редко в stat; смотрите **`edge_*_time`** или перепарсите log.
- **`compute_time`** — основная метрика нагрузки CPU.

### Triangle Counting
- **`sync_bytes` = 0**, **`sync_time` = 0** — норма.
- **`inspect_bytes`**, **`load_bytes`**, **`replication_*`**, **proxies** — заполнены.
- **`total_time_exec`** — главная метрика времени TC.
- Граф **wiki-talk** требует **clean** `.sgr`.

---

## Ограничения и пустые ячейки

1. **Пусто ≠ 0:** ячейка не заполнена, если счётчик не писался в stat и не найден в log.
2. **HSUM vs HMAX:** байты inspection/loading обычно **сумма по кластеру**; таймеры Edge* — **максимум по хостам**.
3. **Только run 0 для `sync_bytes`:** как в официальном `galois_log_parser.R`.
4. **Перезапуск эксперимента:** старый `run.log` мог не содержать байты для прогонов со `SKIP`.
